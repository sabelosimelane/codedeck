# Workflow Start Attachments and Multiline Input — Feature Specification

**Version:** 1.0
**Date:** 2026-11-20
**Status:** Draft

## 1. Overview

A user starting a workflow can review and edit dictated paragraphs and select several local reference files before clicking **Start**. Every agent in the primary run can read the submitted copies from its starting checkout, including on resume.

This specification extends [Workflow Pipelines](2026-11-13-134947-workflow-pipelines-spec.md). The [terminal file drop](terminal-file-drop-spec.md) provides the file-drop interaction and per-file limit precedent. Workflow attachments have their own start and retention rules.

## 2. Run workflow dialog

- Use a text area for descriptive input, including **Feature from requirements** and workflows with a fixed Progress file. Show at least six lines at the normal dialog size, wrap long lines, and allow vertical resizing and scrolling. The dialog itself scrolls on small screens and keeps its controls reachable by keyboard. Keep the existing input label, required indicator and editable draft. Typing, dictation and text paste support paragraphs. Enter inserts a line break and never starts a run from the text area.
- If the selected workflow uses `{input}` in its Progress file setting, keep the single-line path field. Keep current validation, full repo-relative path or fragment handling, repo planning and extra todo runs. On a workflow change, preserve the draft. If a multiline draft is invalid for the newly selected path mode, keep it visible and editable in the text area with a path validation error. Switch to the single-line field once the draft has no line breaks. Never silently discard lines to turn descriptive text into a path.
- Add **Attach files** with a keyboard-accessible multi-file picker and a labelled drop area in the Run workflow dialog. Show the ordered selection, filename, size and a **Remove** action for each entry. Picker and drop append in selection order. Cancelled chooser, empty drops and removing the last file leave the draft usable. Plain text paste retains its normal text-editing behavior.
- Accept regular files of any type, including zero-byte files. Reject directories, unreadable files, files above 20 MiB (20 × 1,024 × 1,024 bytes), selections above 20 files or aggregate bytes above 100 MiB. Exact limits are accepted. Keep separately selected entries with the same name, including repeated selection of the same file. Give each an individually removable row. For mixed selections, add valid entries in order up to the limits and identify each rejected entry and reason without substituting or truncating file bytes.
- Keep the draft and attachments while changing workflow, team, destination or repository. If extra todo runs are selected, display “Attachments go to the primary run only.” Keep each extra run's existing todo input and launch it only after the primary start is accepted. Retain the existing per-run reporting and retry behavior for extra runs.
- Files stay in the dialog until Start. Cancelling before submission discards the draft without uploading or starting anything. While the request is pending, show a starting state and disable edits, duplicate submits and dialog cancellation. On a failed or unconfirmed start, show a readable error and keep text, selected files and launch configuration in the open dialog. Provide explicit retry and allow edits after a definitive rejection. For an unconfirmed outcome or a recoverable provisioning failure, retry the same submission and request ID to resolve the reserved start before editing or starting a fresh submission. If the server confirms a failed unpublished reservation, offer its existing Close run action to abandon it. After Close succeeds, unlock the preserved draft for a fresh submission with a new ID.

## 3. Input and stored data

| Field | Contract |
|---|---|
| Run input | Keep the existing string field and 4,096-character limit. Descriptive input accepts LF, normalizing CRLF and lone CR to LF before validation and persistence. Spaces and line breaks, including blank lines, are preserved in the stored input and in the prompt. Whitespace-only input is blank for existing required-field rules. Preserve the current character-counting convention. |
| Terminal text validation | Apply the current terminal-safe input rules after line-ending normalization, permitting LF for descriptive input and refusing unsafe controls such as NUL and escape. Preserve the current validation and normalization for path input. Keep the 16,384-character composed node prompt limit and the existing launch-guidance bound. Count added attachment guidance against the launch-guidance bound. |
| Run attachments | Add an ordered manifest to the run record. Each entry has a server-generated checkout-relative `path`, validated `name`, integer `sizeBytes`, and internal SHA-256 digest of the submitted bytes. Validate each field and manifest invariants when accepting a request, creating a record or reading persisted data. Migrate existing records to an empty manifest. |
| Run API view | Add `attachments`, an array of `{ name, path, sizeBytes }` in submission order, empty when absent. Its paths are relative to the recorded start checkout and describe the submitted files even if a closed run's checkout is gone. Exclude file bytes, the digest and staging locations. |

Keep required text and path rules and the existing new-task title-or-input rule. Files alone satisfy neither. Explicit task titles and naming eligibility stay the same. For a generated title from multiline input, use the existing naming rule after collapsing runs of whitespace to single spaces, so the temporary title fits its existing one-line field. Keep the full text in the run input regardless of title.

Substitute `{input}` once, preserving the existing template behavior. Render descriptive input in a literal multiline block in both run README and brief using a delimiter that submitted text cannot close. Make attachment references a separate, server-generated section. Never interpret submitted file names as Markdown, terminal commands or instructions. Send the prompt through the existing paste-and-submit path as one submission. Resume and later attempts use the recorded input and manifest.

## 4. API endpoints and request semantics

| Method | Path | Request | Success |
|---|---|---|---|
| POST | `/api/pipelines/runs` | Existing JSON body for attachment-free starts, or multipart form with one `run` field containing that JSON body and repeated `files` file parts | 201 on accepted first start, 200 on matching replay |
| GET | `/api/pipelines/runs/:id`, `/api/pipelines/runs` | Existing detail and paginated list queries | 200 with the additive run view fields from §3 |

The multipart form requires 1–20 `files` parts. Reject missing, null, duplicate or unexpected fields where the declared shape does not permit them. The JSON form and existing place selectors, team options, preflight, pagination, filter allowlist and deterministic sorting stay supported. Apply the existing JSON request bound to the `run` field. Cap the whole multipart request at 100 MiB plus 1 MiB for metadata and framing. Enforce byte limits server-side while streaming before writing beyond the allowed limits.

Use the shared RFC 9457 problem response with `traceId` and indexed `files[n]` field errors where applicable. Use 400 for malformed multipart or JSON, invalid names or parts and invalid input, 413 for count or size limits, 409 for request-ID conflicts or placement state conflicts, and 500 for server storage failures. Keep existing authentication, authorization and destination errors. Validation response details and logs identify the affected field or safe file identity. Omit file bytes, untrusted paths, stack traces and unsanitized names. Keep response and log trace IDs correlated.

The existing start request ID covers the current launch fields and the ordered attachment identities (validated name, size and digest). A matching replay returns the same run or completes its interrupted provisioning under the same reservation. A changed accepted submission with the same ID returns 409, even when the only change is file order or same-size contents. Concurrent matching requests share the reservation and only one can create or enqueue the run. Definitively rejected, uncommitted starts can be retried with the same ID and body. Use a new ID for a corrected submission after definitive rejection. A replay cannot rematerialize attachments for a closed run.

## 5. Provisioning and lifecycle

1. Stream the batch to private server staging under the start attempt. Bind it to that request and the existing start authority. The client supplies bytes and names, never a server path, reusable upload reference or target directory. Require a nonempty basename of at most 255 UTF-8 bytes. Reject separators, dot components, Unicode control and format characters, and invalid UTF-8. Validate the rest of the start, including the resolved project, checkout, Progress file, and prompt bounds, before provisioning. Revalidate placement at publication so concurrent starts cannot bypass destination checks.
2. Use the start reservation and the existing worktree provisioning path. The primary run's starting checkout is the new task worktree, the selected open task worktree, or the selected Main repository. In a multi-repo task, materialize only in the selected **Start in** checkout. Use `<notesDir>/attachments/` under that checkout, with exclusive server-generated per-entry filenames that retain a safe extension when present. Verify containment, safe regular-file writes, run ownership of the directory and Git ignore status before publication. Fail on a symlink, tracked target, unsafe parent or unexpected collision. Keep differently named files and same-name files distinct. A run that starts without attachments creates no attachment directory.
3. Publish the full verified batch and persist its manifest before the first agent launches, including Setup in a new task. For an attached start, return 201 only after publication and manifest persistence, before waiting on agent readiness. Keep the dialog visibly pending during provisioning. A matching replay returns 200 only after publication, or after looking up a previously published run. Attachment-free start timing stays unchanged. Reserve the primary run before provisioning so a lost response can be resolved. A copy or publication failure after reservation leaves one recoverable start with the same ID, no agent launched and no visible ready batch. Report the failure and allow retry using the preserved draft and same ID. Clean partial files and staging on handled failure. A retry can use an already-reserved, validated task or worktree and must not create another one. After a server interruption, reconcile unpublished attempts on startup, remove abandoned staging and safely resume only the matching start on owner retry. Close run on a failed unpublished reservation fences off publication and further retries, clears managed staging and partial files, and uses the existing cleanup rules for any created task or checkout. Once published, retries recognize the complete batch and never overwrite it. After a successful publication, discard staging.
4. Before each step launches, including a resumed or repeated step, verify the listed copies are readable regular files in the recorded checkout and match the recorded byte sizes and digests. Guide each agent to the attachments via the run README and brief, with safe relative paths and original names for identification. Put the instruction and the path to the manifest in the agent guidance for Setup and every node. Keep Setup's Git cleanliness check and its exclusion of home-checkout run notes. If a copy is missing, changed, unsafe or unreadable, report which file is affected and stop before agent launch. Restoring the original bytes permits the existing Resume action.
5. Keep the files for the life of the retained checkout, including when a run is stopped or closed in Main or an open task. A successful cleanup that removes a CodeDeck-owned checkout removes its attachments with it. The existing removal guard may treat only verified, run-owned copies as disposable. A changed copy, unknown content or unsafe path follows the existing cleanup protection. A later run in the same checkout gets a different notes directory and sees only its own attachments in generated guidance.

## 6. Compatibility and scope

Existing terminal drop and paste, ordinary New task, attachment-free clients and older stored runs keep their existing behavior. Preserve workflow definitions, team assignment and overrides, project and worktree eligibility, Progress file validation, Setup behavior, owner approvals, resume and task naming apart from the multiline title adaptation in §3. An attachment never supplies, creates or edits a tracked Progress file. No feature toggle is required.

Out of scope are mid-run attachment changes, clipboard file uploads in the launch dialog, folder uploads, previews, extraction, model-native attachment APIs, changes to dictation or transcription, remote workflow enablement, file sharing across independent runs, and changes to the terminal uploader. Files are available through the filesystem tools of the configured agent. Format interpretation depends on that agent.

## 7. Acceptance criteria

| Case | Observable result |
|---|---|
| Descriptive input in a browser | Open Feature from requirements through Run workflow. Paste or dictate a two-paragraph brief, insert a new line with Enter, edit earlier lines and scroll. Submit once. The stored input, README, brief and captured terminal submission retain the paragraphs. Repeat with a fixed Progress file. A draft containing Markdown fences cannot corrupt the exported note structure. |
| Path workflow and required input | The templated Progress file uses the single-line field. Full repo-relative path and fragment still resolve as before. Invalid paths remain refused. Switching modes preserves the draft and highlights invalid path text. An attached file cannot replace missing required text or an untitled new task's required input. An eligible empty input still works. |
| Selection and failure UX | Drop several fixtures, including two distinct files named alike. Add another through the picker and remove an entry. Cancel the picker and verify the rest stay selected. Unreadable, oversized and directory entries identify the problem. Cancel before Start and observe zero requests. Simulate a failed copy and a lost response. The draft survives and repeat clicks produce one active submission. |
| File visibility | Use a local stub workflow agent to read fixture bytes and inspect the first prompt before any workflow work. Exercise new task Setup, open task, Main and a secondary start repository. The stub reads every selected file from the recorded checkout. Distinct same-name files retain distinct bytes, and `git status --porcelain` puts no attachments in tracked changes. Later and resumed steps receive the same references. |
| Missing or modified files and lifecycle | Delete or change a copy before Resume. Verify a file-specific failure and no agent launch. Restore exact bytes and resume. Close a run in a retained checkout and inspect the preserved copies. Remove a clean owned checkout using existing cleanup and verify disappearance. A changed file or unexpected entry keeps the existing cleanup protection. |
| Independent todo runs | Start a primary and an extra todo run. The extra uses its own todo and has an empty attachment manifest and no attachment references. Fail primary materialization and verify no extra start was dispatched. |
| Input and upload boundaries | Test empty, null and wrong types, whitespace-only required input, line-ending normalization, disallowed controls, exactly 4,096 characters and one over, and the composed-prompt boundary. Test empty batches, zero-byte files, 20 and 21 files, exactly 20 MiB per file and one byte over, and aggregate 100 MiB and one byte over. Assert field errors and trace correlation. |
| Storage and replay | Inject a failure partway through copy, and an interruption before and after publication. Verify no partial agent launch, removal of abandoned staging, same-ID recovery and no duplicated runs, tasks or attachment paths. Race identical requests and replay with changed bytes, order or launch fields. Close a failed unpublished reservation, confirm its replay cannot publish, then edit and resubmit the retained draft with a fresh ID. Attempt traversal, symlink placement, unsafe names and replacement of existing content. Verify an error with no write outside the managed location. |
| Backward compatibility | Replay existing launch fixtures and load older records. Check empty manifests and unchanged attachment-free behavior, team resolution, destination checks, progress planning and terminal upload/drop/paste. Verify existing run list pagination and ordering, additive detail/list views and the standard missing-run problem response. |
