# Role Evals

**Spec**: `docs/specifications/2026-11-28-120211-role-evals-spec.md`
**Status**: Not Started
**Created**: 2026-11-28

Tests use fixture Git repositories made by the tests and scripted terminals in place of
agent CLIs. Nothing here needs a real agent, another repository or the owner's projects.
Spec §11 (which cases to cut first) is guidance for the owner and is not a task.

## Phase 1: Eval cases and validation
> A case can be created from commits, stored with its files, and proved sound without an agent.
> **Inputs:** a local project repository, commits, paths, checks
> **Outputs:** a `ready` case with files under `~/.codedeck/evals/cases/<id>/` and a stored validation
> **Closed when:** unit tests on the pure rules and integration tests against fixture repositories pass, and a case can be made and validated from the Evals tab

- [ ] `eval_cases` table in `server/db.js`, and `server/evals/case-store.js` with a guard per field on every row read (Spec §4.1 — invalid row refused naming the field and id)
- [ ] `shared/eval-cases.mjs`: pure validation of the create and update body, the manifest and each check, reporting every failed field (Spec §4.2, §4.3, §7.1 — all limits and enums)
- [ ] Unit tests: every field of the body, manifest and check at its boundaries, empty and null, and the unknown-enum case (Spec §4.2, §4.3)
- [ ] `server/evals/case-files.js`: build `source.tar`, seed, solution, hidden files, check patches and notes from commits or patch text; all files or none; size limits; a missing or extra file is unreadable (Spec §4.4, §8.1)
- [ ] `server/evals/eval-repository.js`: build the throw-away repository from the snapshot and seed, committed or uncommitted (Spec §8.2 — no other commit, no remote)
- [ ] `server/evals/check-runner.js`: run checks one at a time with timeouts, apply and reverse a check's patch, keep the last 4 KiB of output (Spec §4.3, §8.3, §8.4 scoring)
- [ ] `server/evals/validation.js` and its pure verdict in `shared/eval-cases.mjs`: before and after outcomes, the "cannot fail" rule, solution required for `developer` and `reviewer` (Spec §8.3, §7.3)
- [ ] Unit tests: the validation verdict for every combination of `before`, `expect` and observed outcome, with and without a solution (Spec §8.3)
- [ ] Case state changes: `ready` on a passing validation at the current revision; back to `draft`, revision raised and validation cleared on any change but the name; retire and restore (Spec §5.2, §8.1)
- [ ] `server/routes/evals.js`: `GET/POST /cases`, `GET/PUT /cases/:id`, `PUT /cases/:id/state`, `DELETE /cases/:id`, `POST /cases/:id/validations`, with pagination, allow-listed filters and sorts, RFC 9457 errors and 422 for Git refusals (Spec §6, §7.1–§7.3)
- [ ] Integration tests against fixture repositories: create, 422 leaves no case and no folder, update with a stale revision is 409, validate sound and unsound cases, delete removes the folder; each list dimension of the API standard (Spec §9)
- [ ] `client/src/utils/evalsApi.js` (validated responses) and the **Evals** sub-tab of Settings → Workflows: cases per role with state and last validation, a create and edit form, Validate, Retire, Restore and Delete, with a toast for every outcome (Spec §8.11)
- [ ] Client tests for the cases list and form: field errors shown at the field, validation problems shown in words

## Phase 2: One eval run, scored
> One case is run once by one agent through the run engine and scored by its checks.
> **Inputs:** a ready case, a saved preset agent and an effort
> **Outputs:** an eval run that is `passed`, `failed` or `error` with its reason and results
> **Closed when:** the pure scoring rules are covered and an eval run completes end to end with a scripted terminal

- [ ] `pipeline_runs.purpose` (`work` or `eval`, default `work`) and the exclusions: project run lists, task strip, sidebar counts, Changes, Improvement Loop observations and signals, team scoring and attribution, phone pushes (Spec §4.7, §8.9)
- [ ] `eval_batches` and `eval_runs` tables and `server/evals/run-store.js`, with a guard per field on read (Spec §4.5, §4.6)
- [ ] `shared/eval-scoring.mjs`: pure run verdict from the pipeline run's end state, signal, check outcomes and ticks, with the order of reasons (Spec §8.4, §5.5)
- [ ] Unit tests: every reason of §5.5, the order when several apply, a tick whose task is not found, a null `signal` (Spec §8.4)
- [ ] `server/evals/eval-run.js`: build the eval repository, place the notes, start a pipeline run with `purpose: eval` and the frozen definition (Setup when asked, then the one step), stop it at the time limit, score, close its terminals (Spec §8.4)
- [ ] Step guidance for an eval run: a measurement, no push, pull request, deploy or change outside the eval repository; no automatic answer to NEEDS_INPUT (Spec §8.4)
- [ ] Mapping of pipeline run endings to `error` reasons: CLI dialog, prompt never taken or quota refusal, Setup failure (Spec §5.5, §8.4)
- [ ] `GET /runs`, `GET /runs/:id` (Spec §6, §7.5)
- [ ] Integration tests with a scripted terminal: right change → `passed`; no change → `check_failed`; other signal, wrong tick, NEEDS_INPUT, time limit → the matching reason; a `patch: true` check that must fail; dialog and Setup failure → `error`; the eval repository holds no other commit; an eval pipeline run is absent from every place of §8.9 (Spec §9)
- [ ] Evals tab: an eval run's results (checks with expected, observed, time and output tail; ticks; signal; reason) and read-only access to its terminal and notes (Spec §8.11)

## Phase 3: Batches, the queue and qualification
> An agent is evaluated for a role, and the result is a qualification with its time.
> **Inputs:** a role with at least three ready cases, a saved preset agent and an effort
> **Outputs:** a finished batch, per-case results, and a derived qualification
> **Closed when:** the pure result and qualification rules are covered and a batch runs to `done` with scripted terminals

- [ ] `shared/eval-results.mjs`: pure case result (two of three), early stop, and qualification for a role, agent and effort, including `stale`, `evaluating` and `too_few_cases`; times as medians and their sum (Spec §8.6, §8.7, §5.6)
- [ ] Unit tests: every qualification value in the situations of §8.6; medians with one, two and three passed runs; a batch whose cases no longer match the role's ready cases
- [ ] `server/evals/batch-service.js`: start an evaluation for 1–8 roles as one batch per role, all or none, each refusal named by its role index (three ready cases or 409, preset agent or 409, one working batch per key or 409, `estimatedSec`), cancel a batch (Spec §8.5, §7.7)
- [ ] `server/evals/eval-queue.js`: one eval run at a time, oldest batch first; early stop; one retry after an error; no start while an Improvement Loop replay works, and no replay start while an eval run works; recovery at backend start (Spec §8.5)
- [ ] `GET/POST /batches`, `GET /batches/:id`, `POST /batches/:id/cancellation`, `GET /qualifications` (Spec §6, §7.4, §7.6)
- [ ] Integration tests with scripted terminals: a batch to `done`; the third run cancelled once two agree; an error retried once and then left without a result; three roles in one request give three batches in order, and one refused role creates none; cancel keeps finished results; a restart turns a working run into `interrupted` and the queue goes on; the three 409 refusals; each list dimension of the API standard (Spec §9)
- [ ] Evals tab: the agents table per role (qualification, cases passed, total time, date, sorted by time among those that qualify), **Evaluate** with an effort chooser and the estimated agent time, the working batch with its runs, Cancel; reads every two seconds while a batch is queued or running; a toast for every outcome (Spec §8.11, §8.7)
- [ ] Client tests for the agents table and the batch view
- [ ] `GET /qualifications`: `readyCases`, `estimatedSec`, `canEvaluate` and its reason per row, and rows for custom-command agents (Spec §7.6, §8.6)

## Phase 4: The qualification where agents are chosen, and cases from a run
> The result is seen at the moment of choosing an agent, and a case starts from a real step.
> **Inputs:** qualifications; a finished run's step attempt
> **Outputs:** the qualification in words in three places; a pre-filled case form
> **Closed when:** unit and integration tests pass and the three places show the words

- [ ] Pure wording of a qualification ("Qualified · 48m", "Failed 1 of 3", "Not evaluated", "Evaluating", "Out of date", "Too few cases") in `client/src/utils/` with unit tests (Spec §8.11)
- [ ] Team editor: the wording beside each role's agent and fallback at the chosen effort; nothing disabled (Spec §8.11)
- [ ] Change team dialog of a run: the wording beside each step's agent (Spec §8.11)
- [ ] Improvement Loop trial with subject `team_role`: one line with the candidate agent's qualification, linking to the Evals tab (Spec §1.1, §8.11)
- [ ] `server/evals/case-draft.js` and `POST /case-drafts`: the fields of §8.10 from a run's step attempt; 409 for a role that is not Developer, Reviewer or Tester (Spec §8.10)
- [ ] Unit tests for the draft: each of the three roles, the time limit floor of 600, the notes of the earlier steps of the same round
- [ ] Integration tests for `POST /case-drafts`: happy path per role, unknown run 404, unfinished run 409, invalid body 400 with field errors (Spec §9)
- [ ] Task view: **Make an eval case…** on a finished Develop, Review or Test step, opening the Evals tab's create form with the draft (Spec §8.10)
- [ ] Agents tab: each agent's result per role, the custom-command sentence, and "Evaluating · n of m runs" linking to the batch (Spec §8.12)
- [ ] **Evaluate…** dialog on an agent: effort, roles as tick boxes with disabled reasons, summed agent time, one request on Start, a toast for every outcome (Spec §8.12, §7.7)
- [ ] Notice after a new agent is saved or an agent's revision rises: shown only when a role can be evaluated, starts nothing by itself, **Not now** remembered per agent revision in the browser (Spec §8.12)
- [ ] `client/src/hooks/useEvalBatches.js`: app-wide read of working batches every five seconds while any is queued or running, no overlapping requests, one toast per finished batch and none for a cancelled one (Spec §8.12)
- [ ] Client tests for the wording in the team editor and Change team, the pre-filled form, the Agents tab lines, the Evaluate dialog (ticks, disabled reasons, summed time), the notice, and the finish toast
