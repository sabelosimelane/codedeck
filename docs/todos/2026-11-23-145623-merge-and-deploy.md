## Phase 1: Deploy settings and deploy order
> Each repository of a project can carry a deploy command and a review agent, and the project has a
> saved deploy order, edited in the Repositories… dialog.
> **Inputs:** project config, `pipeline_agents`
> **Outputs:** `repository_deploy_settings`, `project_repository_positions`, their API and UI
> **Closed when:** store, API and dialog tests pass; settings survive a restart of the store

- [ ] `server/deploys/deploy-settings-store.js`: tables `repository_deploy_settings` and `project_repository_positions` with per-field hydration guards (Spec §4, §5, §10.13)
- [ ] Pure validator for a setting body and an order list: command 1–2000 chars, no newline/control characters, `reviewAgentId` UUID or null, revision rules; full-permutation check for the order (Spec §4, §10.9, §12)
- [ ] Unit tests: every validator rule and every hydration guard, including stale revision and duplicate/missing names in the order
- [ ] Pure ordering function: positioned repositories first by position, unpositioned after in stored order (Spec §5)
- [ ] Routes `PUT/DELETE /api/projects/:name/repositories/:repository/deploy-setting`, `PUT /api/projects/:name/repository-order`; `GET /api/projects/:name/repositories` adds `position` and `deploy` (Spec §11, §12)
- [ ] Removing a repository from the list and deleting a project delete its settings and positions (Spec §10.9)
- [ ] `DELETE /api/pipelines/agents/:id` refuses with 409 when a setting uses the agent, naming project and repository (Spec §10.9)
- [ ] supertest integration tests for each route: 200/204, 400 field errors, 404, 409 stale revision and remote project
- [ ] Client: `projectRepositoriesApi.js` calls with validated responses; Repositories… dialog Deploy section (command, review agent select with "No review", Save, Remove) and drag order, toasts on success and failure (Spec §10.12)
- [ ] Component tests for the Deploy section and drag order, including the error toasts

## Phase 2: A manual deploy batch (command and exit code)
> Main's **Deploy** runs a repository's deploy command in its clean main checkout in a tmux pane and records the exit code and log tail.
> **Inputs:** a deploy setting, a clean checkout
> **Outputs:** `deploy_batches`, `deploys`, `deploy_attempts`; batch API; Deploy button, chip and deploy view
> **Closed when:** a real-tmux integration test deploys `echo deployed` to `succeeded` and a failing command to `failed`

- [ ] `server/deploys/deploy-store.js`: the three tables with per-field hydration guards, enum checks, 40-hex commit, attempt number 1–3 (Spec §6–§9, §10.13)
- [ ] Pure state machine for a deploy and a batch: transitions of §9.2, batch status from its deploys, skipping later deploys after a failure (Spec §9, §10.3)
- [ ] Unit tests: every transition, every illegal transition throws, batch outcome for all orderings of succeeded/failed/interrupted
- [ ] Pure precondition check for a batch from Git/run facts: setting present, agent present, checkout exists and clean, branch checked out, no unfinished run, no running batch (Spec §10.2)
- [ ] Unit tests for each refusal reason, naming the repository
- [ ] Terminal attempt runner: new CodeDeck session in the checkout without focus, pane runs `$SHELL -lc <command>` with `remain-on-exit on`, exit from `pane_dead_status`, log tail per §10.6 (Spec §10.1, §10.6)
- [ ] Batch executor: snapshots command/branch/commit at start, runs deploys in position order, one batch per project (Spec §10.1, §10.3)
- [ ] Routes `POST/GET /api/projects/:name/deploy-batches` (paginated, `-createdAt`, `status` filter), `GET /api/deploy-batches/:id`, `POST /api/deploy-batches/:id/close` (Spec §10.10, §11, §12)
- [ ] Integration tests with a temporary Git repository and real tmux: success, non-zero exit, dirty checkout 409, unfinished run 409, second batch 409, two-repository batch with the first failing leaves the second `skipped` and its command never runs
- [ ] Client: `deploysApi.js`; Main strip **Deploy** with disabled reasons, confirmation listing branch/commit/command, status chip, deploy view with attempts, log tails, terminal links and Close; toasts (Spec §10.7, §10.12)
- [ ] Component tests for the button states, confirmation, chip and deploy view

## Phase 3: Review agent and retries
> When the command fails and a review agent is set, the agent reads the result and answers RETRY or STOP; CodeDeck reruns the same command up to three attempts.
> **Inputs:** a failed attempt, the setting's review agent
> **Outputs:** verdicts on attempts, retries, `failed` with the diagnosis
> **Closed when:** integration tests with a stub agent CLI cover RETRY→success, RETRY×3, STOP and no verdict

- [ ] Pure review prompt composer: command, exit code, attempt number, attempts left, log tail, read-only instruction and the `[[CDD:<attempt-id>:RETRY|STOP]]` markers (Spec §10.4)
- [ ] Pure verdict parser for the marker and its reason (≤ 4000 chars), ignoring markers for other attempt ids (Spec §10.4)
- [ ] Unit tests for the composer and parser, including a marker echoed inside the prompt itself not counting as a verdict
- [ ] Review runner: opens the review terminal once per deploy, launches the agent, waits for readiness, resets it before a later review, reads the verdict with the workflow engine's screen reading, 10-minute timeout as an injectable constant (Spec §10.4)
- [ ] Executor wiring: `reviewing` state, retry while attempts < 3, failure details (Spec §9.2, §10.4)
- [ ] Integration tests with a stub agent CLI scripted to print each verdict, and one that asks a question instead (counts as no verdict)
- [ ] Client: deploy view shows `reviewing`, each attempt's verdict and reason, and the review terminal link; component tests

## Phase 4: Merge and deploy
> One press merges a task's repositories with the existing merge and deploys the ones with a setting.
> **Inputs:** a task with one or more open worktrees
> **Outputs:** merge results plus a started (or refused) batch
> **Closed when:** integration tests on real Git repositories cover both endpoints and every merge outcome

- [ ] Pure plan for a whole-task merge: pre-check result per worktree, merge order from deploy order (unpositioned last by name), which merged repositories deploy (Spec §10.5)
- [ ] Unit tests for the plan: any blocked worktree blocks all, order, external repositories merged only
- [ ] Service `mergeAndDeploy(taskId, { worktreeId? })` using `task-landing.js` merge unchanged; stops at the first conflict or refusal and reports `merged`/`conflict`/`refused`/`not_attempted`; starts a batch with `task_worktree_id` set only when every merge succeeded (Spec §10.5, §12)
- [ ] Routes `POST /api/tasks/:id/merge-and-deploy` and `POST /api/tasks/:id/worktrees/:worktreeId/merge-and-deploy`, including the 409 with `blocked` (Spec §11, §12)
- [ ] Integration tests: one-repository success, one-repository conflict (no batch), whole-task pre-check refusal (nothing merged), whole-task second-repository conflict (first stays merged, no batch), batch refused after merges (merges kept, reason returned)
- [ ] Client: `tasksApi.js` calls; **Merge and deploy** on rows and in the header with the merge's disabled reasons, confirmation listing deployed and merge-only repositories, result toasts naming kept merges (Spec §10.7, §10.12)
- [ ] Component tests for both buttons, the confirmation and each result toast

## Phase 5: Restart recovery, pushes and Changes
> Deploys survive a backend restart truthfully, finished batches notify the phone, and Changes shows deploy outcomes.
> **Inputs:** persisted deploys, tmux sessions, the push sender, merged task worktrees
> **Outputs:** recovered or interrupted deploys, pushes, `deploy` on Changes items
> **Closed when:** recovery, push and Changes tests pass

- [ ] Startup recovery: alive pane → watch; dead pane → record exit and continue; session gone → `interrupted` and skip the rest; `reviewing` → `interrupted` (Spec §10.8)
- [ ] Unit tests for the recovery decision per state; integration test with real tmux killing and keeping sessions across a re-created executor
- [ ] Push on batch end ("Deployed …" / "Deploy failed: …") through the existing push sender, and a desktop toast on the same event (Spec §10.11)
- [ ] Tests with a push sender double: exactly one push per finished batch, none for a running one
- [ ] `task-changes.js` and `GET /api/tasks/changes`: latest deploy per landed repository (Spec §10.12, §12)
- [ ] Integration test for the Changes view; client `ChangesDialog.jsx` shows the status or "Not deployed", with a component test
