Follow the Well-Architected Framework for all implementation decisions.

## Architecture at a Glance
```
API Layer (DTOs with primitives)
    ↓ converts to value objects
Business Logic Layer (value objects only)
    ↓ converts to primitives
Data Access Layer (entities with primitives)
```

## Anti-Patterns (Forbidden)

❌ Primitives in business logic layer
❌ Mutable domain objects
❌ Business logic in API or data layers
❌ Generic exception catching
❌ Null parameters without validation
❌ Direct database access from business logic
❌ Infrastructure dependencies in core logic (Spring, repositories, brokers, caches inside evaluators/processors)
❌ Using `ImmutableXxx.Builder` as a return type in `@Value.Immutable` interfaces (causes silent annotation processor failures — return the interface type instead)

✅ Wrap primitives that carry domain meaning or cross boundaries (records for simple wrappers, Immutables for rich entities with cross-field invariants)
✅ Validate at every boundary
✅ Fail fast with clear messages
✅ Immutable objects throughout business layer
✅ Clean layer separation
✅ Technology-independent business logic
✅ Core logic is pure: domain objects in, domain objects out — service layer orchestrates infrastructure around it

## Pre-Commit Checklist

- [ ] No primitives in business logic classes
- [ ] All value objects validate invariants (records: factory method; Immutables: @Value.Check)
- [ ] Preconditions used for business rule validation
- [ ] Bean Validation annotations on DTOs for request validation
- [ ] Clear error messages that guide resolution
- [ ] Immutable objects throughout business layer
- [ ] Core logic is infrastructure-free (no Spring, no repositories, no broker/cache calls)
- [ ] Service layer orchestrates: fetches data → calls pure logic → persists/publishes results
- [ ] Technology abstractions properly implemented
- [ ] Comprehensive test coverage (pure logic unit tests + integration tests)
- [ ] Security annotations on commands
- [ ] Audit logging for business operations
- [ ] Error responses use RFC 9457 ProblemDetail
- [ ] Domain exceptions use sealed hierarchy (ValidationException, StateConflictException, NotFoundException) — never map bare IllegalArgumentException to HTTP status codes

## Frontend Pre-Commit Checklist

- [ ] `unhandledrejection` handler for chunk load errors registered in entry point (before `createRoot()`)
- [ ] Top-level `ErrorBoundary` wraps the app in `App.tsx`
- [ ] `ErrorBoundary` shows "Reload Page" for chunk errors, "Try Again" for generic errors
- [ ] No hardcoded domain error messages on the frontend — all read from `error.message` in API response
- [ ] Generic fallback strings are non-descriptive ("Something went wrong. Please try again.")
